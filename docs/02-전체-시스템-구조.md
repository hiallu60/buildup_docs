# 전체 시스템 구조

## 현재 배포 구조

```text
프론트엔드 앱/웹
      |
      | HTTP API + Bearer Access Token
      v
EC2 / Spring Boot API : 8080
      |
      | VPC 내부 MySQL 연결 : 3306
      v
비공개 RDS / MySQL
```

- 사용자는 데이터베이스에 직접 연결하지 않고 EC2의 API만 호출합니다.
- RDS는 외부에 공개하지 않으며 EC2에서 오는 연결만 허용합니다.
- EC2의 API 포트는 현재 허용된 IP에서만 접근할 수 있습니다.
- 시스템 구성도는 [배포 구조 다이어그램](../diagrams/시스템-구성도.md)에서도 확인할 수 있습니다.

## 애플리케이션 내부 흐름

```text
HTTP 요청
  -> Spring Security 인증/인가
  -> Controller
  -> Service
  -> JPA Repository
  -> MySQL
```

- Spring Security가 JWT를 검증하고 사용자 전역 권한을 구성합니다.
- 서비스 계층이 현장 구성원 여부와 현장별 역할을 추가로 검사합니다.
- JPA는 데이터를 읽고 쓰며, 테이블 정의 변경은 Flyway만 담당합니다.

## 로컬과 배포 환경

| 구분 | 로컬 개발 | 1차 배포 |
|---|---|---|
| 애플리케이션 | 개발자 PC | EC2 |
| DB | `buildup_local` | RDS의 배포 DB |
| DB 공개 여부 | 로컬에서만 사용 | 비공개 |
| 설정 | 로컬 환경변수 | EC2 환경변수 파일 |
| 스키마 관리 | Flyway | 동일한 Flyway 마이그레이션 |

환경마다 DB 주소와 비밀번호는 다르지만, 같은 애플리케이션 코드와 마이그레이션을 사용합니다.

## 배포 흐름

1. 기능 브랜치에서 개발과 로컬 검증을 수행합니다.
2. Pull Request 검토 후 백엔드 기본 브랜치에 병합합니다.
3. EC2에서 검토된 커밋 또는 릴리스 태그를 가져옵니다.
4. 애플리케이션 JAR을 빌드하고 서비스를 재시작합니다.
5. Flyway 상태, 서비스 로그, 헬스 API와 핵심 API를 확인합니다.

## 목표 구조

후속 배포에서는 HTTPS 도메인을 API 앞에 두고, 파일 원본은 S3에 저장합니다. RDS는 계속 비공개로 유지합니다.
