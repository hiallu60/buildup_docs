# GitHub 협업 규칙

## 저장소 역할

- `buildup_backend`: Spring Boot 코드, 테스트, Flyway 마이그레이션
- `buildup_docs`: 배포 상태, DB, API, 프론트 연동, 기술 결정 문서

문서와 구현이 함께 바뀌는 기능은 두 저장소에서 관련 PR을 연결합니다.

## 브랜치

- 기본 브랜치에는 검토와 테스트가 끝난 코드만 병합합니다.
- 기능: `feature/기능명`
- 버그 수정: `fix/문제명`
- 문서: `docs/문서명`
- 긴급 수정: `hotfix/문제명`

예: `feature/report-approval`, `fix/refresh-token-race`, `docs/api-guide`

## 작업 순서

1. 최신 기본 브랜치에서 작업 브랜치를 만듭니다.
2. 한 브랜치에는 하나의 목적만 담습니다.
3. 로컬 테스트와 변경 파일을 확인합니다.
4. Pull Request에 변경 이유, 검증 내용, 영향 범위를 작성합니다.
5. 리뷰 반영 후 기본 브랜치에 병합합니다.
6. 배포 대상은 검토된 커밋 또는 릴리스 태그로 고정합니다.

## 커밋 메시지

```text
feat: 보고서 승인 API 추가
fix: 만료 토큰 오류 처리 수정
test: 자재 요청 권한 테스트 추가
docs: 프론트 연동 안내 갱신
refactor: 현장 권한 검사 분리
chore: 배포 설정 정리
```

## Pull Request 확인 항목

- 요청한 기능과 무관한 변경이 섞이지 않았는가
- 인증·인가와 현장별 권한을 확인했는가
- DB 변경이 새 Flyway 파일로 추가되었는가
- 기존 Flyway 파일을 수정하지 않았는가
- API가 바뀌면 API 및 프론트 연동 문서도 갱신했는가
- 로그나 설정 파일에 비밀정보가 포함되지 않았는가
- 빌드와 관련 테스트 결과를 기록했는가

## 보안 규칙

다음 값은 Git에 커밋하지 않습니다.

- DB 비밀번호
- JWT Secret
- PEM 개인 키
- 실제 운영 환경변수 파일
- 개인 IP와 불필요한 인프라 식별 정보

예제에는 `${VARIABLE_NAME}` 또는 `https://api.example.com` 같은 자리표시자를 사용합니다.

## DB 변경 규칙

- 적용된 `V1`~`V8`을 수정하거나 삭제하지 않습니다.
- 다음 스키마 변경은 `V9__변경_설명.sql`부터 추가합니다.
- 마이그레이션, JPA 엔티티, 테스트와 문서를 한 작업 단위로 검토합니다.
- 운영 DB를 DBeaver에서 직접 수정하지 않습니다.
